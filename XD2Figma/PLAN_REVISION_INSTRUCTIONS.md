# PLAN.md 改訂指示書 — XD → Figma 移植システム設計仕様

対象: `PLAN.md`(Adobe XD → Figma 高再現性・損失検知型移植システム 設計仕様書)
目的: レビューで検出された問題点を修正し、「監査に耐える」と「実データが通る」を両立する仕様に改訂する。
作成日: 2026-07-15

各項目は **[問題] → [修正指示] → [対象セクション]** の形式で記載する。優先度は P0(修正しないと運用が成立しない)/ P1(実装時に必ず突き当たる)/ P2(品質・保守性の改善)の3段階。

---

## P0: 運用が成立しない問題(必須修正)

### P0-1. フォントライセンス許可リストの論理矛盾

**問題**
仕様書自身が「フォントファイル本体はパッケージに含めない」(§2 `fonts.json`)と定めている。フォントを一切転送しない以上、有料フォントの使用にライセンス上の問題は発生しない。移植先の Figma Desktop に同じフォントがインストールされていれば、それはそのマシンで正当にライセンスされたフォントである。したがって §3 フォント処理の手順3–4(無償・OSS ライセンス+ファイルハッシュ完全一致の許可リストによるブロック)は、何も保護しないのにインポートを停止させる過剰装備になっている。

実害も確定的である。ヒラギノ(macOS 同梱)、游ゴシック(Windows/macOS 同梱)は OSS でも無償配布フォントでもないため、現行仕様では日本語 UI デザインの大半が `FONT_LICENSE_BLOCKED` で停止する。またハッシュ完全一致要求は、OS アップデートでフォントファイルが更新されるたびに許可リストを破壊し、恒常的な保守負担を生む。

**修正指示**
1. §3 フォント処理の手順3–4(許可リスト判定によるブロック)を削除する。
2. ブロック条件を次の2つのみに絞る:
   - Figma Desktop の `listAvailableFontsAsync()` に該当 family/style が存在しない → `FONT_NOT_AVAILABLE`
   - `loadFontAsync()` が失敗する → `FONT_NOT_AVAILABLE`
   - 複数 face が曖昧に競合する場合のみ `FONT_FACE_AMBIGUOUS` を維持する。
3. ライセンス情報・vendor・ファイルハッシュの収集(手順1–2)は**監査記録として維持**し、`fonts.json` に記録する。判定には使わない。
4. エラーコード `FONT_LICENSE_BLOCKED` を削除、または「警告(非ブロック)」に格下げする。
5. 将来フォントファイル本体を同梱する機能を追加する場合に限り、ライセンス判定をブロック条件として復活させる旨を「v2 以降の検討事項」として注記する。

**対象**: §2 `fonts.json`、§3 フォント処理手順、§3 ハードエラー一覧、§5-4 CI 受入条件

### P0-2. 視覚差分ハードゲート(SSIM 0.99)の非現実性

**問題**
XD のレンダラー(CoreText / DirectWrite 系)と Figma の独自ラスタライザは、アンチエイリアス、ヒンティング、カーニング、行の折り返し位置が原理的に一致しない。テキストを含むアートボードでは、変換が意味的に完璧でも SSIM 0.99 は日常的に不合格になる。全体停止ポリシーと組み合わさると、視覚差分ゲートが事実上「全ファイル拒否装置」になる。

さらに §4 の合格基準は「SSIM 0.99」「差分画素 1% 以下」「色差各チャンネル 1/255 以内」「座標 0.01px」「角度 0.01 度」が併記されているが、各基準の適用対象(ピクセル比較か、ノード属性検証か)と優先順位が未定義であり、仕様として実装不能である。

**修正指示**
1. 検証を2層に分離して §4 を書き直す:
   - **層1: 構造検証(ハードゲート・維持)** — ノード数、親子関係、z-order、GUID 対応、文字列、style range、画像 SHA-256、メタ情報 deep-equal、座標 0.01px 以内、角度 0.01 度以内、色属性値 1/255 以内。これは**ノード属性の比較**であり、レンダリング結果の比較ではないことを明記する。
   - **層2: 視覚差分(レポート+人間承認)** — XD 基準 PNG と Figma `exportAsync()` の SSIM・差分画素率・差分ヒートマップをアートボード単位でレポート出力する。閾値は「合格/不合格」ではなく「要確認」の振り分けに使い、最終判断は人間が行う。承認結果(承認者・日時・対象アートボード)を変換レポートに記録する。
2. テキストを含む領域はレンダラー差が不可避である旨を仕様に明記し、必要ならテキスト領域をマスクした画素比較をオプションとして定義する。
3. SSIM 計算の実行場所(プラグイン UI 側)と、`exportAsync()` のスケール・フォーマット条件(1x / PNG / sRGB)を仕様に明記する。

**対象**: §4 インポート処理、§5-4 CI 受入条件

### P0-3. 全体停止ポリシーの粒度

**問題**
「1件でもあれば全体停止」(§1)では、4096px 超の写真1枚、Lottie 1個、装飾用の未対応ノード1個でドキュメント全体が移植不能になる。実案件の XD ファイルで blocker ゼロはほぼ期待できず、§5-5 のパイロット移行が開始できない可能性が高い。

**修正指示**
1. 停止の単位を「ドキュメント全体」から「**アートボード単位**」に変更する。blocker を含むアートボードのみ除外し、除外一覧(アートボード名・GUID・理由コード)を変換レポートとインポート結果ページの両方に記録する。
2. 加えて「**記録付き承認続行**」パスを定義する: blocker 一覧を提示し、ユーザーが項目ごとに明示承認した場合のみ続行できる。承認内容(項目・承認者・日時)は変換レポートに永続記録する。「暗黙の劣化はしない」という哲学は維持したまま、「明示的・記録付きの劣化承認」を許容する。
3. 4096px 超画像について、「縮小せず停止」に加えて「ユーザー承認による明示的ダウンスケール(元画像 SHA-256 と縮小パラメーターをメタ情報に記録)」を承認続行パスの一種として定義する。
4. パッケージ生成側(補助アプリ)の停止条件も同じ粒度に合わせる: フォント・画像の問題はアートボード単位で影響範囲を特定し、パッケージ全体の生成拒否は ZIP 破損・スキーマ不一致・ハッシュ不一致など構造的問題に限定する。

**対象**: §1 方針、§3 ハードエラー一覧、§4 インポート処理、§5-5 パイロット計画

## P1: 実装時に必ず突き当たる問題(仕様追記が必要)

### P1-1. パスデータ正規化パイプラインの欠落

**問題**
Figma の `vectorPaths` は **M / L / Q / C / Z のみ対応**(公式ドキュメント確認済み)。A(アーク)・H・V・S・T は不可。XD の `pathData` は SVG パス全般を含みうるため、§3 変換表の「path data、winding、線、gradient、transform を保持」はそのままでは実装できない。

**修正指示**
1. §3 変換表の Path 行に「パス正規化」工程を追記する: A→ベジェ近似、H/V→L、S/T→C/Q への展開を IR 生成時(補助アプリ側)に実施し、`document.json` には正規化済みパスを格納する。元の `pathData` 文字列も監査用に併記する。
2. アーク→ベジェ近似の許容誤差(例: 最大偏差 0.01px 以内、必要に応じてセグメント分割)を数値で仕様化し、構造検証の座標精度 0.01px と整合させる。
3. winding rule(EVENODD / NONZERO)のマッピングを明記する。

**対象**: §2 `document.json`、§3 変換表、§5-2 実装項目

---

### P1-2. 停止条件一覧の欠落項目

**問題**
以下の XD 機能は Figma に対応物がない、または対応が不完全だが、§3 の停止条件一覧に記載がない。

**修正指示** — 次を §3 ハードエラー(または P0-3 適用後の「アートボード単位 blocker」)に追記する:
1. **3D 変換**(rotationX/Y、パースペクティブ): Figma に対応物がない。公開 Scenegraph API で取得可能かが不明なため、**§5-1 実現性ゲートに「3D 変換の検出可否」を追加**する。取得不能な場合は補助アプリの `.xd` 直接解析で検出する。
2. **スタックの個別間隔**: XD の Stack はアイテム間隔を個別調整できるが、Figma Auto Layout の `itemSpacing` は単一値。間隔が不均一な Stack は「Auto Layout 化せず絶対配置 Frame として変換」or「blocker」のどちらかを規則として明記する(推奨: 絶対配置フォールバック+レポート記載)。
3. **背景ぼかしの明度パラメータ**: Figma の background blur に明度調整はない。明度が初期値以外の場合の扱い(blocker or 近似+記録)を定義する。
4. **Repeat Grid のセル差分の可否判定**: テキスト・画像差分は Figma instance override で表現可能、構造差分(要素の追加・削除)は不可。「差分の種類」による変換可否の判定規則を §3 変換表に明記する。

**対象**: §3 変換表・停止条件、§5-1 実現性ゲート

### P1-3. 字間・行送りの単位変換仕様

**問題**
XD の字間は 1/1000 em 単位、Figma の `letterSpacing` は px または %。フォントサイズ依存の変換で丸め誤差が生じ、構造検証の 0.01px 精度と矛盾しうる。また和欧混植テキストで XD が暗黙にフォールバックしたグリフは styleRange 上単一フォントに見えるため、Figma 側で異なるフォールバックが選ばれると視覚差分が出る。

**修正指示**
1. 字間変換式(`letterSpacing_px = charSpacing / 1000 × fontSize`)と丸め規則を仕様化し、構造検証ではこの変換式適用後の値を比較対象とすることを明記する。
2. 行送り(XD lineSpacing = 0 は auto)→ Figma lineHeight のマッピング表を追記する。
3. フォントフォールバックの差異は「視覚差分レポートで検知される既知の非互換」として §4 に注記し、blocker にはしない。

**対象**: §3 変換表(Text 行)、§4 検証

---

### P1-4. 2つのデータソースの整合規則

**問題**
XD プラグイン(公開 Scenegraph API)と補助アプリ(`.xd` 直接解析)が同じ情報を二重取得するが、GUID 突合で不一致が出た場合にどちらを正とするかが未定義。

**修正指示**
1. 原則を明記する: **セマンティクス(型・プロパティ解釈)は公開 API 出力を正とし、公開 API が返さない生データ(画像バイト列・内部メタ)のみ `.xd` 解析を正とする**。
2. 両者が重複して持つ値(座標・サイズ等)が許容誤差を超えて不一致の場合はパッケージ生成を停止し、`SOURCE_MISMATCH` エラーコードを新設する。
3. 併せて構成の簡素化を検討事項として記載する: `.xd` 直接解析で必要情報の大半が取れると実証された場合、XD プラグインの役割を `createRenditions()` による基準 PNG 生成に限定し、エクスポート経路を一本化できる。§5-1 実現性ゲートの結果を受けて判断する旨を注記する。

**対象**: §1 構成、§2 中間形式、§5-1 実現性ゲート

---

### P1-5. 大容量パッケージのメモリ・転送戦略

**問題**
数百 MB の `.xd2fig` をプラグイン UI(iframe)で展開し、base64 で plugin sandbox へ渡す際のメモリ上限・転送方式が未記載。大規模ファイルで最初に破綻するのはこの箇所である。

**修正指示**
1. アセットはアートボード/アセット単位で**チャンク転送**(UI → sandbox へ `Uint8Array` を逐次 postMessage、処理完了ごとに解放)する方式を §4 に明記する。
2. パッケージサイズ・ノード数・画像点数の動作保証上限を仕様値として定め、超過時は事前検査で `PACKAGE_TOO_LARGE` として通知する。
3. §5-1 実現性ゲートに「実案件相当サイズ(目安: 500 アートボード・1GB 級アセット)での転送・メモリ検証」を追加する。

**対象**: §4 インポート処理、§5-1 実現性ゲート

## P2: 品質・保守性の改善

### P2-1. 「sRGB 以外の XD データ」停止条件の検出方法が未定義

**問題**
XD ドキュメント自体はカラーマネジメントを持たない(実質 untagged/sRGB)ため、「sRGB 以外の XD データ」が何を検査するのか不明。埋め込み画像の ICC が Display P3 のケース(P3 スクリーンショット等)は普通に存在する。

**修正指示**
1. この停止条件を「**Figma ファイルの document color profile が sRGB 以外**」のみに限定して書き直す。
2. 埋め込み画像の非 sRGB ICC は blocker にしない: バイト列をそのまま保持・往復検証する現行方式で原本は保全されるため、「非 sRGB ICC 画像を含む」事実をレポートに記載するのみとする。

**対象**: §3 停止条件

### P2-2. クラッシュ時のステージング残骸

**問題**
「例外時にステージングページを削除」はプラグインプロセスの強制終了時には実行されない。

**修正指示**
プラグイン起動時に `__XD_IMPORT_STAGING__` 接頭辞のページを走査し、検出した場合は「前回の中断を検知した」旨を表示して削除(またはユーザー確認後削除)する処理を §4 に追加する。

**対象**: §4 障害回復

### P2-3. `dynamic-page` documentAccess 対応

**問題**
現行の Figma プラグインは `documentAccess: "dynamic-page"` が標準であり、ページの遅延ロード(`loadAllPagesAsync` / `loadAsync`、`setReactionsAsync` 等の async setter)への対応が必要だが記載がない。

**修正指示**
§5-3 の実装項目に「dynamic-page 対応(ページ遅延ロード・async setter 使用)」を追加する。

**対象**: §5-3

### P2-4. 同一 fingerprint 再インポート拒否の緩和

**問題**
ユーザーが旧インポート結果のページを削除して再実行する正当なケースを塞いでいる。

**修正指示**
「同じ source fingerprint の再インポート拒否」を「**同一 fingerprint のインポート結果ページが現存する場合のみ拒否**」に変更する。現存確認はページの plugin data(`xd2fig.migration.v1` 名前空間)で行う。

**対象**: §2

### P2-5. 引用の修正

**問題**
§3 末尾「Adobe 自身が、非表示コンポーネント状態や一部 interaction を XD プラグインに公開していない」の根拠が changelog ページであり、主張を直接裏付けていない。

**修正指示**
XD UXP API リファレンスの該当ページ(interactions モジュール、ScenegraphNode の制約記述)へ引用を差し替えるか、§5-1 実現性ゲートで実証する項目である旨を明記して引用を削除する。

**対象**: §3

## 改訂作業の順序

1. **P0-1 → P0-3 → P0-2** の順で §1〜§4 の方針・停止条件・検証仕様を書き直す(相互に依存するため一括改訂が望ましい)。
2. P1-1〜P1-5 を §2・§3・§5 に追記する。特に P1-1(パス正規化)と P1-2(3D 変換検出)は §5-1 実現性ゲートの検証項目に直結するため、ゲート定義と同時に更新する。
3. P2 群を反映後、変換表(§3)・エラーコード一覧・CI 受入条件(§5-4)の3箇所に矛盾が残っていないか相互参照チェックを行う。

## 改訂後も維持すべき設計(変更禁止)

- 実現性ゲート(§5-1)の「保証できなければ開発停止」構造
- ZIP path traversal・圧縮爆弾・全ファイル SHA-256 検証
- `createImage()` → `getBytesAsync()` のバイト往復検証
- `not-present-in-source` と「取得失敗」の区別
- バージョン別アダプターによる `.xd` 内部形式の隔離
- ステージングページ+ロールバックによる「既存ページ無変更」保証
- 通信・外部アップロード・テレメトリーを行わない方針
